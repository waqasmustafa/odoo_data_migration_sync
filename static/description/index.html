Odoo Data Migration & Sync: Odoo to Odoo Database Migration

Connect two Odoo databases and safely analyze, map, preview, migrate and verify your business data - including cross-version migration into Odoo 18.

Description

Migrating from an old Odoo database (Community or Enterprise) to a new one is normally a painful mix of OpenUpgrade, CSV export/import, and one-off developer scripts. Odoo Data Migration & Sync replaces that with a guided, repeatable workflow: Connect - Analyze - Select - Map - Preview - Migrate - Verify.

Important: This is a data migration and synchronization tool, not a one-click full Odoo database upgrade. It migrates configured business data where compatible target models and fields exist - it does not automatically convert custom module Python/XML/JavaScript code. Target-compatible modules must already be installed on the target database before their data can be migrated.

Supported Migration Paths

This is the Odoo 18 edition of the connector - install it on your Odoo 18 (Community or Enterprise) database as the target, then connect it to any of these source versions:

16 → 18
Odoo 16 Source
17 → 18

Same-Version Transfer
Note: The connector talks to the source over Odoo's standard XML-RPC API, so it works the same way regardless of source version - there is nothing extra to configure per version. Sources on Odoo 16/17/18 Community or Enterprise are all supported by this same module.
Key Features
Guided Migration Wizard

Connect, Select Data, Dry Run / Preview, Migrate, Verify - a clear step-by-step flow for technical and non-technical users alike.

Dry Run / Preview

See exact create / update / skip / error counts before a single record is written to your target database.

Duplicate Prevention

Source/target record mapping plus configurable business-key matching (email, VAT, ref, barcode...) - re-running a migration never creates duplicates.

Dependency-Aware Engine

Companies, Contacts, Categories, Products before Sales/Purchase Orders - with automatic missing-dependency retries across multiple passes.

Record-Level Logs & Retry

Every record's outcome is logged with model, source ID, and error/missing-dependency detail - failed records can be retried individually with one click.

Migration Verification

Post-migration report re-checks the source count against what's actually mapped in the target - Ready / Warning / Blocked per model.

Migration Dashboard

Connections, total runs, success rate, and records created/updated/failed at a glance.

CRM Stage Mapping

Fetch the source CRM stages and map each one to a target stage before migrating leads - opportunities land in the right Kanban column.

Getting Started
Step 1: Add a Connection
Go to Migration → Connections → New. Enter the source server URL, database name, username, and a password or API key. An API key (Settings → Users → your user → Account Security → New API Key) is the recommended, safer option.
Step 2: Test Connection & Detect Version
Click Test Connection to confirm the credentials work, then Detect Version to confirm the source Odoo version. Load Models lists what's available on the source database.
Step 3: (CRM only) Map Stages
If you're migrating CRM Leads/Opportunities, click Fetch CRM Stages on the connection, then map each source stage to a target stage in Migration → CRM Stage Mapping.
Step 4: Dry Run, then Migrate
Click Migrate Data on the connection (or open the Migration Wizard directly), choose what to migrate, run Dry Run / Preview first to review the counts, then click Migrate when you're satisfied.
Step 5: Verify
Open the completed run and click Verify to re-count the source and compare it against what's mapped in the target - a quick Ready / Warning / Blocked summary per model.
What Can Be Migrated?
Contacts
  • Name, Company/Individual type, full Address (Street, City, State, Country), Phone, Mobile, Email, Website
  • VAT, Reference, Job Title, Title, Parent Company (hierarchy preserved)
  • Archived contacts included, so an old Sales/Purchase Order that references one still resolves
Products
  • Product Categories (with hierarchy), Attributes & Attribute Values, Variants
  • Name, Internal Reference/SKU, Barcode, Sales/Purchase price, Image, Tags, Description
  • Product variant combinations are matched by their attribute/value signature, not list position
Employees
  • Departments (with hierarchy) and Employees
  • Work Email/Phone/Mobile, Job Title, Manager, Job Position, Working Hours
  • Time Off / Leave requests, linked to the correct Leave Type and Employee
Inventory (Master Data)
  • Warehouses and Locations (with hierarchy)
Note: Stock quantities/on-hand balances are deliberately not migrated - two databases rarely agree on real-world stock levels, so opening balances should be entered as a deliberate Inventory Adjustment by the business, not copied automatically.
CRM
  • Leads/Opportunities with full contact details, address, expected revenue, probability, priority
  • Salesperson, Sales Team, Tags, Source/Medium, Lost Reason
  • Stage - via the configurable CRM Stage Mapping screen
Projects
  • Projects and Tasks, with Customer, Assignees, Stage, Priority, Deadline, Tags
  • Timesheets, linked to the correct Project, Task, and Employee
Sales & Purchase
  • Sales Orders and Purchase Orders with full line detail (Product, Quantity, Price, Discount, Taxes)
  • Status, Payment Terms, Currency, Salesperson/Buyer
  • Order lines are written once on first creation - re-running a migration safely updates header fields without disturbing lines that may already have deliveries/invoices against them
Point of Sale
  • POS Orders with their product lines
⚠ Important: A POS Shop with the same name must already exist and be configured on the target (payment methods, pricelist, etc. are never auto-created). Payment-method breakdown (cash/card split) is not migrated - only the order and its lines.
Safety & Duplicate Prevention
Nothing Writes Without Dry Run
Every migration can be previewed first. Dry Run reads the source and checks matching/dependencies exactly like a real run, but writes nothing to your target database.
Re-Running Never Duplicates
Every migrated record is linked through an internal source↔target mapping. A second run of the same migration recognizes already-migrated records and updates them instead of creating copies - safe for migration rehearsals and incremental catch-up runs.
Version Differences Degrade Gracefully
Field names that changed between Odoo versions are detected at runtime - a field that doesn't exist on a particular source or target is skipped instead of aborting the whole run, and the skip is logged so you can see exactly what happened.
✅ Duplicate Prevention: Business-key matching (email, VAT, ref, barcode...) is scoped so that a shared value between genuinely different records - e.g. several department contacts using the same company email - never silently merges them into one.
Troubleshooting
Connection Failed Error

Possible Causes:

  • Incorrect URL, database name, username, or password/API key
  • Source server not reachable from this server (firewall, or the source is bound to localhost/127.0.0.1 only)

Solutions:

  • Double-check every field, including the port (default XML-RPC port is 8069)
  • Use an API key instead of the real password (Settings → Users → your user → Account Security)
Records Failing with "Missing Dependency"

This means the record refers to something (a Contact, Product, Category...) that hasn't been migrated yet on this connection.

Solution: Migrate the missing data type first (e.g. Contacts before Sales Orders), then use Migration → Errors → Retry on the failed lines.

CRM Leads Landing in the Wrong Stage

Check: Has Fetch CRM Stages been run, and has every relevant stage been mapped in Migration → CRM Stage Mapping? An unmapped stage leaves the lead on the target's default stage.

POS Orders Not Migrating

Check: Does a POS Shop with the exact same name already exist and is it fully configured on the target? Orders for an unmatched shop are skipped with a clear error rather than silently dropped.

Best Practices
DO
  • Test Connection and Detect Version before your first migration
  • Always run Dry Run / Preview before Migrate
  • Migrate data in dependency order: Contacts → Categories/Products → CRM/Projects → Sales/Purchase/POS
  • Map CRM stages before migrating Leads/Opportunities
  • Rehearse on a staging/test database before touching production
  • Check the Verification report after every migration
DON'T
  • Expect a full Odoo version upgrade (custom module code is not converted)
  • Skip the Dry Run on your first migration of a data type
  • Assume stock quantities were migrated - they're intentionally not
  • Migrate Sales/Purchase Orders before their Contacts and Products
  • Re-run a migration expecting order lines to resync (only header fields update after first creation)
